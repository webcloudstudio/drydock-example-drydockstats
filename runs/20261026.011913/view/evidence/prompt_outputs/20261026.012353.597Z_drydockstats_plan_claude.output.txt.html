# FEATURE: Absent Numbers

| Field       | Value |
|-------------|-------|
| Version     | 20261026 V1 |
| Description | Absent, null, or wrongly typed token counts, cost, and durations count as zero without dropping the record. |
| Depends On  | FEATURE-DuplicateIds.md |
| Provides    | logread.Record numeric fields |
| Consumes    | logread.Read |

## Questions

- None.

## Purpose

The reporter sums token counts, cost, and elapsed time. Real Drydock logs omit `result.stats` for
some calls, write `cost_usd: null` for providers that report no cost, and could carry a field of an
unexpected JSON type. None of these may drop a record or fail the run.

## Behavior

- `result.stats.input_tokens`, `cached_input_tokens`, `output_tokens`, `cost_usd`, and `elapsed_ms`
  are each read independently.
- A field that is absent or JSON `null` counts as zero.
- A field present with a JSON type other than number or `null` (string, boolean, array, object)
  counts as zero and the record is kept (decision Q-004, `zero-keep`).
- A record with no `result.stats` object at all is still a record; every numeric field is zero.
- `result.returncode` that is JSON `null` or absent is recorded as absent, not as zero.
- `result.timed_out` that is absent or not a boolean is recorded as `false`.
- Numbers are decoded with `encoding/json`; integer fields tolerate values written like `12.0`
  only if they are whole numbers, otherwise they count as zero.
- Nothing here writes to the log being read.

# FEATURE: Model Attribution

| Field       | Value |
|-------------|-------|
| Version     | 20261026 V1 |
| Description | Each record is attributed to the executed model, falling back to the requested model, under its provider. |
| Depends On  | FEATURE-AbsentNumbers.md |
| Provides    | logread.Record.Model |
| Consumes    | logread.Read |

## Questions

- None.

## Purpose

`job.model` is the requested model alias (for example `sonnet`), while `result.stats.model` is the
model that actually ran (for example `claude-sonnet-5-5`). Reports group by what ran, and fall back
to the request only when the log does not say.

## Behavior

- A record's model is `result.stats.model` when it is present and a non-empty string.
- Otherwise the model is `job.model`.
- A `result.stats` object without `model`, a missing `result.stats`, a `null` model, or an empty
  string model all fall back to `job.model`.
- The provider of a record is `job.llm`.
- The model and provider are exposed on the record for the models and failures reports.

# FEATURE: Date Options

| Field       | Value |
|-------------|-------|
| Version     | 20261026 V1 |
| Description | The --since and --until option values are accepted only as real calendar dates written YYYY-MM-DD. |
| Depends On  | FEATURE-CommandLine.md |
| Provides    | cli date validation |
| Consumes    | ddkstat <report> [--target] [--since] [--until] <log> |

## Questions

- None.

## Purpose

Date filters compare against the first 10 characters of `started_at`, so an option value must be
exactly that shape and must name a day that exists.

## Behavior

- A valid value is exactly ten characters: four-digit year, `-`, two-digit month, `-`, two-digit day.
- The value must also be a real calendar date, checked with `time.Parse` and the `2006-01-02`
  layout; leap days are honored (`02-29` is valid only in a leap year).
- Rejected: month 13, day 30 in February, non-padded forms such as `2026-1-5`, compact forms such
  as `20261014`, trailing or leading characters, an empty value, and any non-date text.
- The validator is a pure function in `internal/cli` returning the date text and an error; the
  parser maps its error to a usage error (exit handling is owned by FEATURE-UsageErrors.md).

## Required Go Tests

The build writes these tests in package `./internal/cli`:

- `TestParseDateAcceptsRealDates`
- `TestParseDateRejectsMalformed`
- `TestParseDateRejectsImpossibleDates`

# FEATURE: Usage Errors

| Field       | Value |
|-------------|-------|
| Version     | 20261026 V1 |
| Description | Every usage error exits 2 with nothing on standard output and a usage line on standard error. |
| Depends On  | FEATURE-DateOptions.md |
| Provides    | exit code 2 |
| Consumes    | cli date validation |

## Questions

- None.

## Purpose

Operators and scripts distinguish a mistyped command (exit 2) from an unreadable log (exit 1).

## Behavior

- Exit 2, with empty standard output, for: no arguments; an unknown report; an unknown option
  (including `--help`, decision Q-001 `unknown-exit-2`); an option missing its value; an invalid
  date value; a missing log path; more than one log path.
- Usage errors are decided before the log is opened, so a usage error never becomes exit 1 even if
  the named log does not exist.
- One usage line is written to standard error naming each of the six reports (`summary`,
  `commands`, `targets`, `models`, `daily`, `failures`) and each of the three options (`--target`,
  `--since`, `--until`). Standard error is never compared by acceptance.
- A repeated option is not a usage error: the last occurrence wins (decision Q-002).

## Required Go Tests

The build writes this test in package `./internal/cli`, writing the usage line to a `bytes.Buffer`
and checking it names every report and every option:

- `TestUsageLineNamesReportsAndOptions`

## Programmatic Acceptance

=== AC usage-errors-exit-2 ===
Intent: Each kind of usage error exits 2 and writes nothing to standard output, with an existing log path supplied.
Requires: executable=go; scope=test

import json
import os
import tempfile
from drydock_go import cli_runner

fd, log = tempfile.mkstemp(suffix=".jsonl")
with os.fdopen(fd, "w", encoding="utf-8") as f:
    f.write(json.dumps({"execution_id": "a", "started_at": "2026-10-14T00:00:00.000Z",
                        "status": "succeeded",
                        "job": {"command_name": "build", "target": "T"}}) + "\n")

cases = {
    "no-args": [],
    "unknown-report": ["frobnicate", log],
    "missing-log": ["summary"],
    "unknown-option": ["summary", "--colour", "red", log],
    "help-option": ["summary", "--help", log],
    "extra-log": ["summary", log, log],
    "missing-value-target": ["summary", "--target"],
    "missing-value-since": ["summary", "--since"],
    "missing-value-until": ["summary", "--until"],
    "bad-since-month": ["summary", "--since", "2026-13-01", log],
    "bad-until-day": ["summary", "--until", "2026-02-30", log],
    "bad-since-form": ["summary", "--since", "2026-1-5", log],
}
try:
    for name, args in cases.items():
        code, out, err = cli_runner(*args)
        print(name, code)
        print(err)
        assert code == 2, (name, code, out, err)
        assert out == "", (name, out)
finally:
    os.unlink(log)
=== END AC usage-errors-exit-2 ===

# FEATURE: Unreadable Log

| Field       | Value |
|-------------|-------|
| Version     | 20261026 V1 |
| Description | A log that cannot be opened or read exits 1 with nothing on standard output. |
| Depends On  | FEATURE-LogReading.md, FEATURE-CommandLine.md |
| Provides    | exit code 1 |
| Consumes    | logread.Read, ddkstat <report> [--target] [--since] [--until] <log> |

## Questions

- None.

## Purpose

An operational failure reading the log is reported differently from a usage error so that callers
can tell a bad invocation from a bad environment.

## Behavior

- A log path that does not exist, cannot be opened, or cannot be read exits 1.
- A directory named as the log path is unreadable and exits 1 (decision Q-003, `exit-1`).
- One diagnostic line is written to standard error; standard output stays empty.
- Report output is buffered until the whole log has been read, so a read error after some lines
  were consumed cannot leave partial standard output.
- This applies to every report name.
- The log is only ever opened for reading.

## Required Go Tests

The build writes this test in package `./internal/cli`, using a reader that fails partway through:

- `TestReadErrorLeavesStdoutEmpty`
