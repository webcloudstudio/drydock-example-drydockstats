# Feature: CSV Report Writer

| Field       | Value |
|-------------|-------|
| Version     | 20261024 V1 |
| Description | Writes report rows as CSV with a header row, LF line endings, and optional TOTAL rows. |
| Depends On  | ARCHITECTURE.md |
| Provides    | CSV writer for report rows |
| Consumes    | — |

## Questions

- None.

## Purpose

Every report shares one CSV writer. It writes a header row first, then data rows, comma-separated with `\n` line endings. Zero-match reports write their header and, where the report defines one, a zero TOTAL row.

## Behavior

- The first row written is the report header, exactly as the report defines it.
- Each subsequent row is written as comma-separated fields, terminated by `\n`.
- Line endings are `\n` only; no `\r\n`.
- A zero-match report writes its header and, where the report has a TOTAL row, a TOTAL row carrying zero values.
- The writer does not add quoting to plain values. Values in this product are alphanumeric, numeric, or dates, and contain no commas, quotes, or newlines.

## Programmatic Acceptance

# Feature: Whole-File Skipped Count

| Field       | Value |
|-------------|-------|
| Version     | 20261024 V1 |
| Description | Counts skipped log lines over the whole file, independent of any filter. |
| Depends On  | ARCHITECTURE.md, FEATURE-LogSkip.md, FEATURE-FilterTarget.md, FEATURE-FilterDate.md |
| Provides    | whole-file skipped count |
| Consumes    | record parser, target and date filters |

## Questions

- None.

## Purpose

The `skipped` column of the summary report counts skipped lines in the entire log, regardless of `--target`, `--since`, or `--until`. Filters narrow the records a report aggregates; they never change the skipped count.

## Behavior

- The skipped count is the number of non-blank lines that the record parser rejects, computed over every line of the file.
- The count is computed before filters are applied, so `--target` and the date options have no effect on it.
- Blank lines are not counted (see FEATURE-LogRead.md).
- Running the same log with and without filters yields the same skipped count.

## Programmatic Acceptance

=== AC skipped-ignores-target ===
Intent: The skipped count is identical with and without a --target filter.
Requires: executable=python3; scope=test

    f.write("not json\n")
    f.write('{"schema_version":1,"execution_id":"e2","started_at":"2026-10-14T06:37:54.176Z","status":"succeeded","job":{"command_name":"build","target":"B","llm":"claude","model":"haiku"},"result":{"returncode":0,"timed_out":false}}\n')

# Feature: Summary Report

| Field       | Value |
|-------------|-------|
| Version     | 20261024 V1 |
| Description | Produces the one-row summary report over the filtered records. |
| Depends On  | ARCHITECTURE.md, FEATURE-SkippedCount.md, FEATURE-LogFailed.md, FEATURE-LogNumbers.md, FEATURE-FilterTarget.md, FEATURE-FilterDate.md, FEATURE-FormatCSV.md, FEATURE-FormatMinutes.md, FEATURE-FormatCost.md |
| Provides    | summary report |
| Consumes    | skipped count, record aggregates, CSV and format helpers |

## Questions

- None.

## Purpose

The summary report answers the operator's first question: how many records ran, how many succeeded or failed, over what date span, and what tokens, cost, and minutes they used.

## Behavior

- Writes one data row under the header `records,skipped,succeeded,failed,first,last,input_tokens,cached_tokens,output_tokens,cost_usd,minutes`.
- `records` is the count of filtered records; `skipped` is the whole-file skipped count.
- `succeeded` and `failed` partition the filtered records by status.
- `first` and `last` are the earliest and latest start dates (first 10 characters of `started_at`) among filtered records, empty when none match.
- Token columns are the sums of the filtered records' values; absent values count as zero.
- `cost_usd` is written with `%.4f`; `minutes` is written in tenths of a minute.
- A zero-match run writes the header and one zero row (`0,<skipped>,0,0,,,0,0,0,0.0000,0.0`).
- Exit code is 0 whenever the log can be read, including when no record matches.

## Programmatic Acceptance

# Feature: Commands Report

| Field       | Value |
|-------------|-------|
| Version     | 20261024 V1 |
| Description | Produces one row per command, ordered by calls then command name, plus a TOTAL row. |
| Depends On  | ARCHITECTURE.md, FEATURE-FilterTarget.md, FEATURE-FilterDate.md, FEATURE-LogNumbers.md, FEATURE-LogFailed.md, FEATURE-FormatCSV.md, FEATURE-FormatMinutes.md |
| Provides    | commands report |
| Consumes    | record aggregates, CSV and format helpers |

## Questions

- None.

## Purpose

The commands report shows which Drydock commands ran, how often, how many failed, and what tokens and minutes they used.

## Behavior

- Header: `command,calls,failed,input_tokens,cached_tokens,output_tokens,minutes`.
- One row per distinct `job.command_name` among filtered records.
- Rows are ordered by `calls` descending, then `command` ascending by byte value (AC-006).
- Each row's `minutes` is written in tenths of a minute (FEATURE-FormatMinutes.md).
- A final `TOTAL` row aggregates all filtered records.
- A zero-match run writes the header and one row `TOTAL,0,0,0,0,0,0.0`.

## Programmatic Acceptance
